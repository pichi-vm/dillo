# PMI launch boundary

Baselines and method: [README](README.md). This report covers the launch source paths. The
requirement register records complete scoped dispositions; source inspection
does not establish native initialization behavior.

## L-001 — Producer and consumer retain obsolete boot-state schema

Rules examined: PMI-001 (selected target semantics), PMI-003 (BSP initial
state), MODEL-003 (realization before execution). Scope: shared Dillo parser
and launch handoff, Arma manifest producer, Tatu x86/Arm entry construction.
Verdict: **violates**, source-confirmed for the schema/entry boundary.

Current PMI `src/vm/mod.rs:19` defines `Spec<P>` where P is the architecture's
CPU profile. It has no vCPU-state field and denies unknown fields. `spec/vm.md`
requires actions in order followed by architecture-defined BSP initialization.
`spec/x86-64.md:20` specifies protected-mode entry with paging disabled at
`0xFFFFFFF0`; `spec/aarch64.md:45` specifies EL1 entry at zero and listed
register initialization. Unspecified fields must not be relied upon.

Dillo `src/lib.rs:212,272,627` still stores architecture register structures
and the removed generic `pmi::cpu::Profile`, decodes `Spec<CpuState>` and
extracts `spec.vcpu`. `src/main.rs:2618` prepares CPU inputs using that supplied
state. Current CI uses the older locked PMI dependency, so passing builds/boots
do not establish compatibility with the current PMI contract.

Arma `src/manifest.rs:213` emits the old vCPU field, programs x86 paging/long
mode using Tatu's page-table and GDT addresses, and sets Arm PC to `tatu.entry`
at `src/manifest.rs:306`. Tatu's x86 stub at
`deps/tatu/src/arch_x86_64.rs:88` enters Rust under the long-mode assumption.
Its Arm stub at `deps/tatu/src/arch_aarch64.rs:32` establishes stack/bootinfo
then branches to Rust; it does not constitute entry-at-zero placement.
The linker packs other sections before Arm text. Arma additionally initializes
Arm FP/SIMD access outside PMI's promised boot-state fields; entry code must
establish any such state it requires.

Existing owners: [Dillo #131](https://github.com/pichi-vm/dillo/issues/131),
[Arma #47](https://github.com/pichi-vm/arma/issues/47). Their live issue bodies
were fetched; both remain open. The source findings still apply at the newly
pinned baselines. No new duplicate launch-contract issue is needed.

Interface consequences:

- Shared launch selects the architecture/target schema and validates profiles;
  it does not accept an arbitrary image-supplied BSP register object.
- The selected Machine family's CPU preparation initializes the target's BSP
  on its native owner; AP preparation remains distinct and guest-directed.
- Arma supplies conformant image placement/actions; Tatu owns its required
  post-entry mode transition and setup, rather than having the host infer it.
- Acceptance must include current-PMI producer/consumer tests on both guest
  architectures and native backend lanes. Native fixed-register coverage and
  AP-state behavior still need individual audit records.

## L-002 — Action identity loses its own destination

Rules examined: PMI-002 (each action retains destination and ordered semantics).
Scope: Dillo shared parser/action representation and launch write derivation.
Verdict: **violates**, source-confirmed representation/consumption path.

`src/lib.rs:249` stores Load/Fill with section name (and fill kind), but no GPA.
`resolve_actions` at line 718 explicitly discards the action destination after
the section table has been assigned a GPA. `guest_writes` at
`src/main.rs:1898` obtains destination from `parsed.sections[section]` for each
action. Multiple actions referring to one source section therefore cannot
retain distinct destinations through this representation.

Owner: [#133](https://github.com/pichi-vm/dillo/issues/133), with
reconciled evidence and acceptance criteria.
The launch interface needs immutable source descriptors separate from ordered
operations carrying their own destination, extent and semantics.

## L-003 — Launch recipe omits zero operations

Rules examined: PMI-002 (Data/Padded/Zero semantics), LIFECYCLE-001 (launch
recipe/reconstruction implications). Scope: shared launch-write generation.
Verdict: **violates**, source-confirmed recipe semantics.

`guest_writes` skips loads whose file size is zero and emits only raw file
bytes for other loads. It does not emit the Padded tail as a zero operation.
`apply_load_sections` writes only the generated byte slices. Allocator initial
zeros do not implement the ordered semantics, and replay cannot restore bytes
the guest changed in these omitted ranges.

Existing owner: [#134](https://github.com/pichi-vm/dillo/issues/134). Fresh
reconstruction is the adopted reboot policy; its implementation must still
execute exact zero semantics instead of relying on a fresh allocator. The
launch contract must represent and account for zero extents explicitly.

## L-004 — Retained file identity does not retain launch contents

Rules: PMI-002 stable inputs, LIFECYCLE-001 retained recipe. Scope: all hosts;
Linux also has a mutable file-backed initial mapping. Verdict: **violates**.

`src/main.rs:1519` keeps an ordinary open file, maps it on Linux or reads it
elsewhere, and drops the backing after loading. The reboot path remaps/rereads
that same file while retaining old parsed metadata and write operations.
The handle prevents pathname substitution, but not modification/truncation of
the same underlying file. The initial owned buffer on non-Linux hosts is
stable once read; the Linux mapping and subsequent rereads have no demonstrated
immutability guarantee. Guest/debug changes to RAM are a separate source of
mutation and must not alter a future retained source.

New owner: [#157](https://github.com/pichi-vm/dillo/issues/157). No native race
or SIGBUS probe was run. A stable source handle must mean stable content, not
merely an open file; native mechanisms and copy costs require qualification.

## L-005 — Arm CPU profile requirements are not enforced

Rules: PMI-001 CPU requirements. Scope: KVM AArch64 and HVF AArch64.
Verdict: **violates**, source-confirmed omission.

KVM `deps/dillo-machine-kvm/src/hypervisor.rs:381` discards `cpu_profile`
on non-x86, then initializes the host-preferred target with PSCI and AP power
flags. HVF `deps/dillo-machine-hvf/src/lib.rs:578` accepts `_cpu_profile`
without validation. Current PMI has multiple Arm v8/v9 profiles; parsing an
architecture-specific value does not establish the guest-visible feature floor.

By comparison, KVM x86 `hypervisor.rs:340` checks mandatory CPUID features
before applying supported CPUID, and WHP `hypervisor.rs:293` validates its
profile before vCPU creation. This is evidence of a validation path, not full
current-profile native qualification. Additional supported features are
permitted on PMI's ordinary `vm` target and are not inherently a violation.

Tracked in updated [#131](https://github.com/pichi-vm/dillo/issues/131).
Native mandatory-feature/refusal tests remain required on every applicable
backend; there was no new native experiment in this pass.

## L-006 — CPU preparation and release are not a finalized-machine boundary

Rules: PMI-003/004 and CPU-001. Scope: shared launcher and all four native
lanes. Verdict: **violates** for the adopted preparation/owner/release contract.

The current launcher does perform actions and attachment before calling
`run_vcpus` (`src/main.rs:2717`); failures propagated before that call prevent
entry. However, `Machine::prepare_vcpu_run` is a default no-op and there is no
machine-bound successful-finalization capability. The CPU API exposes
`run(&self)` on a shareable object without a launch permission argument.

KVM `lib.rs:703` and WHP `lib.rs:377` create/program native CPUs during attach
on the launcher, then run them behind a mutex on execution threads. HVF
`lib.rs:801` creates/programs native CPUs on the owner thread inside `run_cpu`,
with no shared pre-entry readiness/finalization barrier. CPU threads are spawned
one by one and can enter immediately, before later logical workers have
acknowledged readiness. Current stop-on-error is not prelaunch finalization.
Deferred native AP creation is permitted by the design and is not itself a
launch violation; its later failure must reach the supervisor.

AP handling is not uniformly absent: KVM Arm creates APs powered off; KVM x86
uses in-kernel INIT/SIPI startup; HVF AP workers wait for guest PSCI entry/context
before native creation. HVF `secondary_state` at `lib.rs:971` also copies PSTATE
and CPACR from the image-supplied BSP structure. Native AP semantics, including
WHP behavior, remain qualification work rather than assumed from a wrapper.

The fixed-state replacement must account for every specified field. Current
x86 setters (`KVM hypervisor.rs:413`, `WHP hypervisor.rs:488`) program the old
register map plus TR/LDTR; they do not explicitly establish DR6/DR7, PAT, XCR0
or FP state. Current Arm setters (`KVM hypervisor.rs:506`, `HVF
hypervisor.rs:226`) do not explicitly set SP_EL0. Absence of an explicit write
does not prove a native reset value is wrong: native defaults and normalization
are **unverified** and require evidence. The old image-driven state is itself
the proven incompatibility.

Owners: [#131](https://github.com/pichi-vm/dillo/issues/131) and native evidence
[#151](https://github.com/pichi-vm/dillo/issues/151). Required contract separates
logical worker readiness, native preparation, finalized launch permission and
guest-directed AP startup. All native creation/destruction stays on the runner
owner; normal execution does not gain general register access.

## Revalidated existing launch findings

`resolve_actions` enforces Zero shape only in the bootconfig branch; DT fill
shapes remain unchecked there (#142). `tests/pmi_adversarial.rs:117` has an
empty test body, and several cases return successfully without `/tmp/real.pmi`
(#145). These findings were re-read in the current source. Historical isolated
probe and CI results are evidence at their recorded revisions, not new runs.

`git diff --name-status 0f09b45..c808d800` reports only DESIGN.md: runtime,
tests and lockfile are identical to the preceding audit. This supports carrying
forward unchanged-path observations with their original execution limitations;
the new requirements and changed policy still require fresh interpretation.

Issues #133 and #134 were updated to current rules and the fresh-reconstruction
policy. #18 now tracks fresh reconstruction rather than perpetuating an in-place
RAM-replay remedy. Their published bodies were fetched and compared to drafts.
